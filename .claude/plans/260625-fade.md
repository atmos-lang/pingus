# Plan: Fade (Screen Transition)

Port of C++ `ScreenManager::fade_over`: reveal the next screen
through a centered box (~0.5-1s) over the current screen.
The current screen is the backdrop; only the top screen is
interactive during the transition.

Lives in `main.atm` (`Fade` task), driven from the menu dispatch
(`260624-menu.md`, `260625-main.md`).

## Status

- [x] push transition (`main.atm`): `Fade(cur, Next, ...)` snapshots
  `cur` and `toggle cur(false)` IMMEDIATELY (only `Next` is live,
  matching the original's frozen old screen), then grows `Next` over
  the frozen `:snap` backdrop; resumes `cur` on return
- [x] pop (fade-out): on return, `toggle cur(true)` (resume live
  menu), screenshot the dying `Next` into `:snap`, shrink it on
  `world` over the live menu. KEY FIX: `pre`/`post` are scoped in
  `watching 500ms` so they abort after the grow and don't cover the
  pop.
- [x] smooth timing: both pcts are clock-driven with a `while`
  in the loop header — `loop us on :clock while p<1` /
  `... while q>0` (rate `(us/1e6)*2` = 100% / 500ms), clamped with
  `math.min(1, ...)` / `math.max(0, ...)`. The `while` terminates
  each driver (pop ends at `q<=0`). Matches C++ (`elapsed * 2`).
  Per-tick delta capped with `math.min(us, 40000)` (~one 40ms
  frame) as a safeguard against a large first tick.
  OFFSCREEN CAVEAT: smoothness is NOT verifiable headless — the
  xvfb env doesn't pace its clock to wall-time like a vsync'd
  display, so a clock-driven anim races 0.5s of game-time into a
  tiny wall window (push looks instant in screenshots) while the
  earlier timer version happened to be capturable. So: VERIFY
  smoothness + the pop on a REAL display. If it still jumps there,
  fall back to fine timer steps (`loop in 50 { await 10ms;
  set p += 0.02 }`), which is wall-paced.
- [x] verified offscreen: push grows over frozen menu, pop shrinks
  to reveal the live menu (parallax resumes). The clip box is
  centered (`['%', x=0.5, y=0.5, ...]` defaults to center anchor).
  Both directions work.
- [ ] option E (per-screen layers) only if wanted later

### A. Original snapshot + freeze + clip-grow

Screenshot the menu, `toggle menu(false)` to freeze it, then clip
`world` to a box growing 0->1 to reveal the incoming screen.
Dropped: the clip was a no-op in expert mode (the bug), and "new
grows" needs the incoming screen on the front layer anyway.

### B. Scale the snapshot (no clip)

```
pico.output.draw.layer(:snap, ['%', x=0.5, y=0.5, w=(1-p), h=(1-p)])
```

Draws the snapshot on `window` shrinking toward center; the live
`Next` on `world` shows around it.
Works without clip, but the effect is the old screen *scaling*
down, not the original box reveal.
Replaced by C once clip was fixed.

### C. Clip-wipe the snapshot (current in `main.atm`)

```
pico.set.layer(:window)
pico.set.scene [ clip = ['%', x=0.5, y=0.5, w=(1-p), h=(1-p)] ]
pico.output.draw.layer(:snap, ['%', x=0.5, y=0.5, w=1, h=1])
pico.set.scene [ clip = ['%', x=0.5, y=0.5, w=1, h=1] ]   ;; reset
```

Snapshot on `window`, clipped to a box shrinking 1->0; the old
frame wipes away (rectangular) to uncover `Next` on `world`.
Inverse direction of the original ("old recedes" vs "new grows")
but rectangular, matching the box aesthetic.
Needs the expert clip fix. No reorder, no per-screen layers.

### D. Live menu + grow the incoming clip

Insight: the menu need not fade — it stays live as the backdrop;
the *incoming* screen fades in via a clip growing 0->1.
No screenshot, no `toggle`.
This is the literal original ("new grows from center").

Requirement: backdrop (full) and incoming (growing clip) must be
separable, so the incoming must draw on the FRONT layer (`window`)
while the menu stays on `world`.
On a single shared layer one clip would hit both.
Fragile on a shared layer (draw order + sticky-clip reset).

### E. Separate layers `:menu` / `:screen` (recommended)

Two named child layers of `world`, same dim as the window:

```
pico.layer.empty(:world, :menu,   true, ['!', w=800, h=600])
pico.layer.empty(:world, :screen, true, ['!', w=800, h=600])
```

- each task draws to its own layer (`pico.set.layer(:menu)` /
  `:screen`, restoring `:world` after so the env `clear()`
  cascades to both);
- `:screen` composites in front of `:menu`;
- `Fade` controls each layer independently: clip `:screen` to a
  growing box (fade in), optionally `toggle` the menu task.

`scene.clip` is already a per-layer property, so this is the
robust realization of F: each screen owns its clip, set by `Fade`,
but the renderer enforces separation (no shared-clip ordering or
stickiness hacks).

### F. Per-task clip `pub` (shared layer, fallback)

Each task exposes a `pub` holding its clip rect; before its
`:draw` it applies `pico.set.scene [ clip = pub ]`; `Fade`
animates the pubs from outside (`set t.pub = box`).

Lighter (no extra layers) but re-inherits the shared-layer
hazards: draws must be ordered backdrop->screen, and the clip must
be reset to full each frame (sticky + env clear).

### E vs F

| concern             | F (clip pub, shared)   | E (per-screen layer) |
|---------------------|------------------------|----------------------|
| where the clip lives| task `pub`, re-applied | layer `scene.clip`   |
| separation          | by draw order          | by compositing       |
| sticky / clear reset| manual, every frame    | automatic, per-layer |
| Fade control        | `set t.pub`            | `set <layer>.clip`   |
| extra setup         | none                   | create the 2 layers  |

### G. Fade brackets Next with clip spawns (shared layer)

`Fade` receives `Next` and controls the clip from outside by
spawning, in order, around it:

```
task Fade (Next, ...) {
    var p = 0.0
    spawn {                                 ;; pre: before Next's draw
        loop on :draw {
            pico.set.scene [ clip = ['%', x=0.5, y=0.5, w=p, h=p] ]
        }
    }
    pin nxt = spawn Next(...)               ;; draws on world, clipped
    spawn {                                 ;; post: after Next's draw
        loop on :draw {
            pico.set.scene [ clip = ['%', x=0.5, y=0.5, w=1, h=1] ]
        }
    }
    watching 1s {
        loop on 100ms { set p = p + 0.1 }
    }
    await(nxt)
}
```

Per frame the draw order is menu (spawned earliest) -> pre -> Next
-> post, so: menu draws full, pre clips `world` to box(p), Next
draws inside the box, post restores full (for the env `clear()`
and the menu's next frame).
Result: the incoming screen grows from center over the live menu,
on the shared `world` layer.

No screenshot, no extra layers, no per-task layer code, no
`toggle`.
Like F it relies on draw order + the sticky-clip reset, but the
reset is centralized in the `post` spawn (not scattered per task),
and all control lives in `Fade`.
Constraint: the backdrop (menu) must be spawned before `Fade`, and
every screen must draw on `world`.

## Recommendation

Two finalists:

- G (bracketed clip spawns) — lightest "new grows"; no layer-API
  unknowns, all control in `Fade`. Order-enforced.
- E (separate layers) — most robust; renderer-enforced separation,
  no draw-order/sticky reliance, but needs the layer binding to
  cooperate.

Start with G (least machinery, nothing new to validate); fall back
to E if the shared `world` clip proves fragile across real screens.

## Fade-out (return / pop)

The options above are the *push* (fade-in).
For the *pop* (back), diverge from the original (which fades only
on push) and clip the OUTGOING screen inward to reveal the
previous one.

Steps — the outgoing screen is terminating:

1. screenshot the dying screen into `:snap` (it stops drawing once
   it returns, so capture its last frame);
2. `toggle prv(true)` — resume the previous screen, paused while
   this one was on top; it is now live underneath;
3. fade out: draw `:snap` on `window` (front), clipped/shrunk
   inward 1 -> 0, uncovering the live `prv` on `world`;
4. terminate `Fade`.

Implications:

- keep-alive + suspend model: `prv` is paused (`toggle prv(false)`)
  while the top screen is active and resumed on return — not
  terminated. So `prv` (the menu) is kept alive (already
  `pin menu = spawn Menu()`), and `Fade` must receive `prv` to
  toggle it.
- likely `Fade (prv, Next, ...)` owns the whole lifecycle: push
  (grow `Next` over live `prv`, then `toggle prv(false)` once
  covered) -> `await nxt` -> pop (snapshot, `toggle prv(true)`,
  shrink `:snap`).
- push and pop become near-symmetric: push grows the incoming, pop
  shrinks the outgoing, each over the other screen.
